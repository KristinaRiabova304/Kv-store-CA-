# ADR-0005: Які security groups я роблю і хто з ким може говорити

- Статус: прийнято
- Дата: 2026-11-01, оновлено 2026-11-04 після AI-рев'ю

## У чому питання
Таблиці маршрутів вирішують, *куди* трафік узагалі може піти. Але вони не вирішують,
*хто* може підключитися до конкретного сервера і на який порт. Для цього в AWS є
**security group** - файрвол, який прикріплюється до сервера.

Як працює security group:
- за замовчуванням увесь вхідний трафік заборонено, я дописую лише дозволи;
- вона **stateful**: якщо запит пропустили всередину, відповідь на нього вийде назовні автоматично;
- джерелом у правилі може бути не лише діапазон IP, а й **інша security group**.
  Тоді правило означає: пускати будь-який сервер, до якого прикріплена та група.

У M2 з'являться балансувальник, coordinator і шарди. Мені треба наперед вирішити,
хто до кого може звертатися.

## Які були варіанти
1. **Одна security group на всіх.** Найпростіше. Але тоді шард можна відкрити для того самого
   трафіку, що й балансувальник, і будь-яка помилка в правилах відкриває все одразу.
2. **Правила за діапазонами IP**, наприклад пускати на шард усе з `10.20.0.0/16`. Працює,
   але пускає будь-який сервер у VPC, а не лише coordinator. І ламається, якщо зміняться підмережі.
3. **Окрема група для кожної ланки, і правила посилаються одна на одну.** Шард пускає лише
   сервери з групою coordinator, coordinator пускає лише сервери з групою балансувальника.

## Що я вирішила
Варіант 3. Ланцюжок такий:

```
інтернет --80--> kvstore-edge-sg --8080--> kvstore-coordinator-sg --9090--> kvstore-shard-sg
```

| Група | Кого пускає | Порт | Для чого |
|---|---|---|---|
| `kvstore-edge-sg` | будь-кого з інтернету, `0.0.0.0/0` | 80 | балансувальник у публічних підмережах |
| `kvstore-coordinator-sg` | лише `kvstore-edge-sg` | 8080 | coordinator |
| `kvstore-shard-sg` | лише `kvstore-coordinator-sg` | 9090 | шарди |

Порти 8080 і 9090 - це параметри шаблону `CoordinatorPort` і `ShardPort`. Якщо в M2 я оберу
інші, міняю лише параметр.

**SSH, порт 22, я не відкриваю ніде.** Відкритий SSH - часта причина зламу серверів.
Робочого способу зайти на приватний сервер у мене поки немає: SSM потребує ролі на сервері й мережевого шляху
до сервісу, а EC2 Instance Connect потребує порту 22. Це відкрите питання для M2, див. нижче.

**Вихідний трафік** лишаю дозволеним за замовчуванням. Поки шарди стоять у приватних підмережах без NAT,
маршруту в інтернет у них немає. Це тримається лише на розміщенні, тому в M2 я перегляну це правило.

**HTTPS, порт 443, поки не відкриваю.** Для нього потрібен сертифікат, а це вже M2 разом із балансувальником.

## Що з цього випливає
- Плюс: шард не досяжний ні з інтернету, ні з інших серверів VPC, лише від coordinator.
- Плюс: якщо додам новий шард чи coordinator, правила не треба міняти: достатньо прикріпити до нього потрібну групу.
- Плюс: security groups безкоштовні.
- Мінус: у M3 шарди мають обмінюватися даними між собою для реплікації. Тоді я додам правило
  `kvstore-shard-sg` → `kvstore-shard-sg` і напишу про це ADR.
- Мінус: HTTP на порт 80 не шифрується. Для M1 це нормально, бо серверів ще немає, але в M2 треба буде HTTPS.
- Де це в коді: ресурси `EdgeSecurityGroup`, `CoordinatorSecurityGroup`, `ShardSecurityGroup` в `infra/network.yaml`.

## Відкриті питання для M2
Цей ланцюжок описує лише шлях запиту від клієнта до шарда. AI-рев'ю показало, чого йому бракує.
Я не додаю це зараз, бо застосунку ще немає, але перед M2 мушу вирішити:

1. **Шард до coordinator.** Завдання M2 вимагає, щоб шард реєструвався в coordinator при старті.
   Зараз це заблоковано, потрібне правило `kvstore-shard-sg` → `kvstore-coordinator-sg`.
2. **Доступ і деплой на сервери.** Від результату `scripts/check-passrole.sh` залежить, чи можна дати серверу роль.
   Без цього CI/CD не зможе доставити код на приватний сервер.
3. **Клієнт YCSB.** Йому потрібна своя група або доступ через балансувальник.
4. **Де жити групам.** ADR-0002 тримає в `kv-network` те, що рідко змінюється, а правила змінюватимуться часто.
   Експортовані ID груп не можна міняти, поки їх імпортує інший стек, тому перенести групи в окремий стек
   треба до появи стека застосунку.
5. **HTTP з інтернету.** Публічний сертифікат потребує власного домену, якого в мене немає.
   Варіанти: обмежити доступ за IP або чесно лишити HTTP.
