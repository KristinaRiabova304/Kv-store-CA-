# ADR-0006: Протокол і формат API - REST з JSON, контракт в OpenAPI

- Статус: запропоновано
- Дата: 2026-11-10

## У чому питання
Клієнти, YCSB і шарди мають якось говорити з coordinator. Мені треба вибрати протокол,
формат даних і спосіб записати контракт, щоб він був до коду, а не після.

## Які були варіанти
1. **REST + JSON, контракт в OpenAPI.** Кожна операція - HTTP-метод на шлях запису.
   Можна перевірити звичайним `curl`. OpenAPI-файл читають і люди, і інструменти.
2. **gRPC + Protocol Buffers.** Бінарний формат, швидший, строгі типи в `.proto`.
   Але `curl` не підходить, для YCSB треба писати свій клієнт, і демо на захисті складніше.
3. **GraphQL.** Добре, коли клієнт сам вибирає поля зі складних зв'язаних даних.
   У сховищі ключ-значення зв'язків немає, тож це лише зайвий шар.

## Що я вирішила
Варіант 1. Операції лягають на HTTP-методи природно:

- CREATE - `PUT /tables/{table}/items/{pk}[/{sk}]`. Саме `PUT`, бо повторний запит дає той самий результат;
- READ - `GET` на той самий шлях;
- EXISTS - `HEAD` на той самий шлях: `200` або `404` без тіла;
- DELETE - `DELETE`: завжди `204`, навіть якщо запису не було, з тієї ж причини;
- реєстрація таблиці - `POST /tables`, повторна назва дає `409`.

Значення запису - JSON-об'єкт до 400 КБ, як ліміт запису в DynamoDB.
Шарди говорять з coordinator тим самим REST, лише на порту 9090 і під шляхом `/internal`.

## Що з цього випливає
- Плюс: демо і перевірка через `curl`, без спеціальних клієнтів.
- Плюс: контракт `api/openapi.yaml` написаний до коду, тести перевіряють, що код йому відповідає.
- Мінус: JSON і HTTP/1.1 повільніші за gRPC. На кожен запит клієнта coordinator робить ще один HTTP-запит до шарда.
  Це додає затримку, яку видно в YCSB. Якщо в M3 це стане проблемою, внутрішній протокол можна замінити, не чіпаючи клієнтський.
- Мінус: немає автентифікації. Доступ обмежую мережею, ADR-0009.
- Де це в коді: `api/openapi.yaml`, обробники HTTP в `internal/coordinator`.
