# ADR-0010: Доставка коду через S3 і CI/CD у GitHub Actions з ключами сесії sandbox

- Статус: запропоновано
- Дата: 2026-11-10

## У чому питання
Код треба доставити на сервери, а шарди стоять у приватній підмережі без інтернету.
Ще треба конвеєр, який сам деплоїть зміни інфраструктури й застосунку.

Що заважає в sandbox:
- не можна створювати IAM-ролі, тож не можна дати серверу свою роль для S3 і не можна налаштувати
  вхід GitHub в AWS через OIDC;
- LabRole немає, чи можна дати серверу наявний instance profile, ще треба перевірити `scripts/check-passrole.sh`;
- ключі доступу живуть лише одну сесію, приблизно 4 години.

## Які були варіанти доставки
1. **NAT gateway**, і сервер сам завантажує код з GitHub. ≈$33 на місяць лише за NAT.
2. **SSH або SSM.** SSH закритий за ADR-0005. SSM потребує ролі на сервері й платних interface endpoints.
3. **S3 gateway endpoint і bucket policy.** Gateway endpoint для S3 безкоштовний і додає в таблицю маршрутів
   маршрут лише до S3, не в інтернет. Бакет дозволяє `s3:GetObject` лише запитам, що прийшли через мій endpoint.
   Тоді серверу не потрібні ні роль, ні ключі.

## Які були варіанти CI/CD
1. **GitHub Actions + OIDC.** Без постійних ключів. Потребує IAM-ролі, sandbox це забороняє.
2. **AWS CodePipeline.** Теж потребує сервісної ролі.
3. **GitHub Actions + ключі сесії sandbox у секретах репозиторію.** На початку кожної сесії я
   оновлюю секрети командою `scripts/set-ci-creds.sh`, вона викликає `gh secret set`.

## Що я вирішила
Доставка - варіант 3, CI/CD - варіант 3.

Як проходить деплой:
1. Push у `main` → тести → збірка двох бінарників Go для Linux.
2. Збірка йде в `s3://kvstore-artifacts-<акаунт>/releases/<коміт>/`.
3. Конвеєр оновлює стеки: `kv-network`, `kv-artifacts`, потім `kv-app` з параметром `ReleaseVersion=<коміт>`.
4. Зміна параметра змінює user data серверів. CloudFormation зупиняє і знову запускає сервер,
   systemd-служба при старті читає версію з user data, завантажує бінарник з S3 і запускає його.

Як сервер стартує вперше: user data лише завантажує з S3 `bootstrap.sh` і запускає його.
Скрипт ставить службу `kvstore`. Перед кожним стартом служба через IMDSv2 читає рядок `# KV_VERSION=` з поточної
user data і завантажує бінарник цієї версії. Сам сервер працює від тимчасового користувача без прав.
Ті самі кроки `scripts/deploy-all.sh` я можу запустити й вручну, CI лише викликає цей скрипт.

Якщо `check-passrole.sh` покаже, що наявний instance profile можна дати серверу, я все одно лишаю bucket policy
з endpoint, бо вона працює без жодної ролі.

## Що з цього випливає
- Плюс: жодного NAT, SSH чи ролі. Приватні підмережі лишаються приватними.
- Плюс: тести і збірка працюють завжди, навіть коли лаба вимкнена. Деплой можливий лише в активній сесії.
- Мінус: **дані в пам'яті зникають при кожному деплої**, бо сервер перезапускається. Для M2 прийнятно,
  збереження з'являється в M3. Після AI-рев'ю це хоча б видно: шард реєструється з новим `bootId`,
  coordinator пише попередження і рахує `restarts`. А з `EXPECTED_SHARDS=2` записи не приймаються,
  поки після деплою не повернуться обидва шарди.
- AMI закріплений конкретним ID, а не «останнім» з SSM, інакше новий образ AWS перетворив би деплой на заміну серверів.
- Мінус: ключі сесії лежать у секретах GitHub. Вони спливають за 4 години, але поки дійсні, дають усі права
  моєї ролі. Репозиторій публічний, тому секрети доступні лише запускам з `main`, не з форків.
- Мінус: деплой залежить від мене: якщо я забула оновити ключі, крок деплою падає. Повідомлення про це має бути зрозумілим.
- Де це в коді: `.github/workflows/ci.yaml`, `infra/artifacts.yaml`, `infra/app.yaml`, `scripts/set-ci-creds.sh`.
