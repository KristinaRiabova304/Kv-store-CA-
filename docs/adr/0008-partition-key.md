# ADR-0008: Стратегія partition key - шард вибирається за таблицею і partition key

- Статус: запропоновано
- Дата: 2026-11-10

## У чому питання
Ключ запису складений: partition key і, за бажанням, sort key. Наприклад, у таблиці `orders`
partition key - користувач `u1`, sort key - дата `2026-11-10`. Треба вирішити, що саме хешувати,
щоб вибрати шард.

## Які були варіанти
1. **Хешувати лише partition key.** Тоді ключ `u1` у таблицях `users` і `orders` завжди
   потрапляє на один шард. Популярні значення на зразок `admin` збираються на одному шарді з усіх таблиць.
2. **Хешувати таблицю, partition key і sort key.** Розподіл найрівніший, але записи одного користувача
   розкидані по всіх шардах. Щоб прочитати замовлення `u1` за місяць, треба питати всі шарди.
3. **Хешувати таблицю і partition key.** Усі записи одного partition key в одній таблиці лежать на одному шарді,
   а різні таблиці розподіляються незалежно.

## Що я вирішила
Варіант 3, як у DynamoDB. Хешується рядок `<таблиця>\x00<partition key>`. Байт `\x00` розділяє частини,
тому пара (`ab`, `c`) не збігається з парою (`a`, `bc`).

Sort key у вибір шарда не входить. Він визначає порядок записів усередині partition key на шарді.
Тому діапазонний запит `?from=&to=` іде лише на один шард, і шард повертає записи вже відсортованими.

## Що з цього випливає
- Плюс: діапазонні запити за sort key йдуть на один шард.
- Плюс: різні таблиці не заважають одна одній.
- Мінус: **гарячий partition key**. Якщо один користувач має мільйон записів або отримує більшість запитів,
  усе це падає на один шард, і додавання шардів не допоможе. Клієнт має вибирати partition key
  з великою кількістю різних значень: ID користувача, а не країну чи статус.
- Мінус: розмір одного partition key обмежений пам'яттю одного шарда.
- Для YCSB: його ключі на зразок `user6284781860667377211` мають багато різних значень і sort key не використовують,
  тож бенчмарк перевіряє саме рівномірний розподіл.
- Де це в коді: функція, що будує ключ для кільця, в `internal/coordinator`; сортування в `internal/store`.
