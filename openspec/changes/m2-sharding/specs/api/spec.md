# Специфікація API

Повний контракт у `api/openapi.yaml`. Тут описано поведінку, яку перевіряють тести.

## ADDED Requirements

### Requirement: Реєстрація таблиці
Клієнт SHALL мати змогу зареєструвати таблицю з назвою, назвою partition key
і, за бажанням, назвою sort key. Назва таблиці: латиниця, цифри, `_` і `-`, від 3 до 64 символів.

#### Scenario: нова таблиця
- **WHEN** клієнт надсилає `POST /tables` з `{"name":"users","partitionKey":"userId"}`
- **THEN** coordinator відповідає `201` і повертає визначення таблиці

#### Scenario: таблиця вже існує
- **WHEN** клієнт реєструє таблицю з назвою, яка вже є
- **THEN** coordinator відповідає `409` і не змінює наявне визначення

#### Scenario: перегляд таблиць
- **WHEN** клієнт надсилає `GET /tables` або `GET /tables/{table}`
- **THEN** coordinator повертає список таблиць або одну таблицю, для невідомої таблиці `404`

### Requirement: CREATE - записати запис
Клієнт SHALL записувати запис за ключем. Значення - будь-який JSON-об'єкт до 400 КБ.
Якщо запис з таким ключем уже є, він замінюється.

#### Scenario: запис у таблицю без sort key
- **WHEN** клієнт надсилає `PUT /tables/users/items/u1` з JSON-тілом
- **THEN** coordinator відповідає `200` і запис можна прочитати

#### Scenario: запис у таблицю з sort key
- **WHEN** таблиця має sort key і клієнт надсилає `PUT /tables/orders/items/u1/2026-11-10`
- **THEN** запис зберігається під ключем (`u1`, `2026-11-10`)

#### Scenario: неправильна форма ключа
- **WHEN** таблиця має sort key, а клієнт його не передав, або навпаки
- **THEN** coordinator відповідає `400`

### Requirement: READ - прочитати запис
#### Scenario: запис є
- **WHEN** клієнт надсилає `GET` на шлях запису
- **THEN** coordinator повертає `200` і те саме значення, яке було записано

#### Scenario: запису немає
- **WHEN** клієнт читає ключ, якого немає
- **THEN** coordinator відповідає `404`

### Requirement: EXISTS - перевірити, чи є запис
#### Scenario: перевірка
- **WHEN** клієнт надсилає `HEAD` на шлях запису
- **THEN** coordinator відповідає `200`, якщо запис є, і `404`, якщо немає, без тіла

### Requirement: DELETE - видалити запис
#### Scenario: видалення
- **WHEN** клієнт надсилає `DELETE` на шлях запису
- **THEN** coordinator відповідає `204`, і наступний `HEAD` повертає `404`
- **AND** видалення ключа, якого немає, теж повертає `204`, бо результат той самий

### Requirement: Діапазон за sort key
Для таблиці з sort key клієнт SHALL мати змогу прочитати записи одного partition key
у порядку sort key, з межами `from`, `to` і `limit`.

#### Scenario: замовлення одного користувача за листопад
- **WHEN** клієнт надсилає `GET /tables/orders/items/u1?from=2026-11-01&to=2026-11-30&limit=50`
- **THEN** coordinator повертає записи `u1`, у яких sort key між `from` і `to` включно, відсортовані за зростанням

### Requirement: Помилки в одному форматі
Кожна відповідь з помилкою SHALL мати тіло `{"error": "<код>", "message": "<текст>"}`.
Якщо шард недоступний, coordinator SHALL відповідати `503`, а не зависати: тайм-аут до шарда 2 секунди.
Якщо кластер ще не готовий (див. специфікацію `sharding`), coordinator SHALL відповідати `503` з кодом `cluster_not_ready`.
