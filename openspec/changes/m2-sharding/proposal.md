# Change proposal: M2 - шардування навантаження

## Навіщо
Один сервер має межу: пам'ять, CPU і мережу. Щоб сховище могло рости, я розкладаю дані
по кількох серверах-шардах. Кожен шард тримає лише свою частину ключів. Хто де лежить,
вирішує coordinator через consistent hashing: так при додаванні шарда переїжджає
лише невелика частина ключів, а не всі.

## Що я роблю
- **API.** Специфікація REST у форматі OpenAPI: реєстрація таблиці та операції над записами
  EXISTS, CREATE, READ, DELETE. Ключ складений: partition key + sort key, sort key необов'язковий.
  Файл `api/openapi.yaml`, рішення в ADR-0006.
- **Coordinator** на Go. Приймає запити клієнтів за цим API. Якщо жодного шарда не зареєстровано,
  працює в режимі одного вузла і зберігає дані сам.
- **Шарди** на Go. Зберігають записи в пам'яті. При старті реєструються в coordinator
  і далі раз на 10 секунд підтверджують, що живі.
- **Кільце consistent hashing** у coordinator. Хеш xxHash64, 128 віртуальних вузлів на шард, ADR-0007.
  Хешується назва таблиці + partition key, тому всі записи одного partition key лежать на одному шарді, ADR-0008.
- **Інфраструктура кодом.** Новий стек `kv-artifacts` (S3-бакет для збірок) і стек `kv-app`
  (coordinator і 2 шарди на EC2 `t3.micro`). У `kv-network` додаю S3 gateway endpoint
  і експорт ID групи шардів. Розміщення в ADR-0009.
- **CI/CD** у GitHub Actions: тести → збірка → завантаження збірки в S3 → оновлення стеків
  `kv-network`, `kv-artifacts`, `kv-app`. ADR-0010.
- **Бенчмарк YCSB** з окремого клієнтського сервера. Цифри зберігаю як базу для порівняння в M3 і M5.

## Чого я не роблю в M2
- Реплікацію і збереження на диск. Шард тримає дані в пам'яті, після перезапуску вони зникають. Це M3.
- Перенесення ключів при додаванні шарда. Кільце вже перераховується, але старі ключі
  лишаються на старому шарді. Це M5.
- HTTPS, автентифікацію клієнтів, балансувальник. Доступ до coordinator обмежую security group, ADR-0009.
- Кілька coordinator-ів. Coordinator один, і це вузьке місце, про це в ADR-0009.

## Що з'явиться
- Нові теки: `api/`, `cmd/coordinator`, `cmd/shard`, `internal/`, `.github/workflows/`, `bench/`.
- Нові шаблони: `infra/artifacts.yaml`, `infra/app.yaml`.
- В AWS: S3-бакет, S3 gateway endpoint (безкоштовний), 3 сервери `t3.micro`,
  1 публічна IPv4 для coordinator, на час бенчмарку ще 1 клієнтський сервер.

## Рішення, для яких я пишу ADR
- ADR-0006: протокол і формат API (обов'язковий)
- ADR-0007: хеш-функція і кількість віртуальних вузлів (обов'язковий)
- ADR-0008: стратегія partition key (обов'язковий)
- ADR-0009: де стоять coordinator, шарди і клієнт YCSB; закриває відкриті питання ADR-0005
- ADR-0010: як код потрапляє на сервери і як працює CI/CD у sandbox
- ADR-0011: мова Go і зберігання в пам'яті

## Ризики, які перевіряю першими
- Чи дає sandbox створити S3-бакет із bucket policy та VPC endpoint. Без цього план доставки коду змінюється.
- Чи можна дати серверу наявний instance profile, `scripts/check-passrole.sh`. Якщо так, доставка простіша.
- Чи приймає YCSB `rest` binding мій формат API. Запасний план: go-ycsb з власним драйвером.
